# Этап 0. Аудит NextOrders (nextorders/food)

Дата аудита: 2026-11-09. Базовый коммит upstream: `ea6da5b` (v2.0.0-alpha.2, 493 коммита).

## 1. Исходное состояние (проверено запуском)

| Проверка | Команда | Результат |
|---|---|---|
| Установка | `pnpm install --frozen-lockfile` (pnpm 10.32.1, Node 25.8) | OK |
| Unit-тесты | `pnpm vitest run --project unit` | **без сборки food-schema: 1 файл падает** (`core/api.test.ts` — нет `dist`). После `pnpm --filter @nextorders/food-schema build` (как в CI): **20 файлов, 98 тестов — зелёные** |
| Typecheck | `pnpm -r run typecheck` | OK (предупреждения volar о `vue-router/volar/*` — не ошибки) |
| Сборка web-app | `nuxt build` | OOM на дефолтном heap; OK при `NODE_OPTIONS=--max-old-space-size=8192` |
| E2E | `pnpm test:e2e` (Playwright, chromium, поднимает `nuxt dev` для essence и web-app) | **нестабильны**: параллельно 22/29 (таймауты cart/checkout), последовательно 28/29 (другой тест — resilience). Причина — on-demand компиляция `nuxt dev` в webServer. Для нашего CI E2E переводятся на собранный `.output` |

Вывод: проект в рабочем состоянии; сборка требует увеличенного heap, E2E нестабильны из-за dev-серверов — оба пункта учитываются в нашем CI.

Прочее в рабочей копии: `main.py` — пустой шаблон PyCharm (не трогаем, не входит в продукт).

## 2. Текущее устройство

```
apps/web-app            Nuxt 4 SSR витрина (одна витрина = один деплой, channelId из env)
apps/web-app-selector   Экран выбора города/канала
apps/essence            Демо-бэкенд: in-memory Map, статические данные. "Not for production"
packages/food-schema    Zod-схемы + Gateway-протокол (единый POST с {type, body})
packages/core           Nuxt layer: BFF-роуты /api/* → fetchApi(gateway), pinia-сторы channel/options
packages/ui             Nuxt layer: @nuxt/ui тема, i18n (11 языков), useDictionary
e2e/                    Playwright: smoke, cart, checkout, navigation, localization, resilience
docker/                 Dockerfile на каждое приложение (node:24-alpine, non-root, healthcheck)
```

Поток данных: браузер → Nuxt server route (`packages/core/server/api/*`) → `POST {NUXT_API_URL}` с `Authorization: NUXT_API_TOKEN` → внешний бэкенд, реализующий Gateway. Сессия гостя — запечатанная cookie `nuxt-auth-utils` (`orderId`, `completedOrderIds`).

Корзина = **серверный черновик заказа** (`status: draft`): `addOrderItem` / `increment` / `decrement` возвращают пересчитанный заказ. Это хорошо ложится на серверный расчёт цен.

## 3. Сильные стороны

- Качественная SSR-витрина: mobile-first, PageSpeed-ориентированная, SEO-страницы категорий/товаров.
- Чистое разделение «витрина ↔ бэкенд»: UI не знает, откуда данные. Бэкенд заменяется без переписывания UI.
- Готовые сценарии: каталог, варианты товара, корзина, доставка/самовывоз, слоты времени, подсказки адресов, зоны доставки, оплата наличными со сдачей, экран «заказ оформлен».
- Русская локализация уже есть (`packages/ui/i18n/locales/ru-RU.ts`).
- Nuxt layers (`ui`, `core`) — естественная точка переиспользования для Telegram и admin.
- Лицензия MIT, зависимости пермиссивные (см. §6).

## 4. Ограничения и проблемы

| # | Проблема | Влияние на нашу модель |
|---|---|---|
| P1 | **Нет мультитенантности.** `channelId` задаётся env на деплой; tenant не определяется по Host. | Второе кафе = второй деплой. Противоречит главному критерию успеха. |
| P2 | **Нет модификаторов/добавок** — только `variants` (размер/вес). | Требование MVP (п.4 сценария) не покрыто схемой. |
| P3 | **Деньги — `number` (float)**, без валютной дисциплины. | Нужны целые копейки в API. |
| P4 | `order/complete.post.ts` делает `{...order, ...clientBody}` и валидирует `OrderSchema.partial()` — **клиент может прислать `totalPrice`, `status`, `items`**. Защита полностью делегирована бэкенду. | Наш бэкенд обязан игнорировать любые клиентские цены/статусы — так и спроектирован API (поля просто отсутствуют во входных схемах). |
| P5 | Статусы заказа `draft/created/ready/delivered` — без машины состояний. | Заменяется явной FSM на бэкенде. |
| P6 | Gateway — RPC через один POST, без OpenAPI, без версионирования. | Не годится как контракт для 3 клиентов. |
| P7 | BFF-роуты существуют только в Nuxt-сервере → **SPA-сборка (Capacitor) не может их использовать**. | Мобильный клиент и Mini App должны ходить в API напрямую. |
| P8 | Ошибки сторов глотаются (`catch {}`), пользователь не видит причину. | Нужен единый формат ошибок + отображение. |
| P9 | `useOrderStore` автосохраняет контакты в черновик каждые 2 с (PATCH). | Нормально для черновика корзины; ПДн попадают в БД до оформления — учесть в retention. |
| P10 | Нет админки, уведомлений, оплаты онлайн, аудита, тестов бэкенда. | Создаётся с нуля. |
| P11 | i18n: `detectBrowserLanguage.alwaysRedirect`, дефолт `en`. | Для РФ дефолт должен быть `ru`, локаль — настройка тенанта. |
| P12 | Сборка требует >4 GB heap. | Учитываем в Docker/CI. |
| P13 | E2E гоняются на `nuxt dev` — flaky. | E2E на production-сборке. |
| P14 | Часовой пояс канала — фиксированное смещение (`+03:00`), не IANA. | Летнее время в РФ отменено, но для корректности используем IANA (`Europe/Moscow`) на бэкенде; адаптер отдаёт смещение. |

## 5. Решение по повторному использованию

| Компонент | Решение | Комментарий |
|---|---|---|
| `apps/web-app` (страницы, компоненты) | **Использовать, адаптировать** | Каталог, товар, корзина, checkout. Добавить модификаторы, статус заказа, Telegram-адаптер. |
| `packages/ui` | **Без изменений + расширение** | Тема и i18n; брендинг тенанта через runtime app config/CSS-переменные. |
| `packages/core` сторы | **Адаптировать** | Перевести с BFF-gateway на типизированный клиент нашего API. |
| `packages/core/server/api/*` (BFF gateway) | **Заменить** | SSR ходит в FastAPI напрямую, передавая Host. Gateway-прокси выводится из эксплуатации после миграции. |
| `packages/food-schema` | **Сохранить как view-model витрины**, не как контракт API | Источник истины контракта — OpenAPI бэкенда. Адаптер `api → food-schema` в `packages/core`, чтобы не переписывать компоненты разом (см. ADR-0003). |
| `apps/essence` | **Оставить для upstream-тестов**, не развивать | Заменяется FastAPI. Удалим, когда e2e переедут на наш бэкенд. |
| `apps/web-app-selector` | **Не использовать в продукте** | Выбор «городов» = элемент маркетплейса. Для нескольких филиалов одного кафе выбор филиала делается внутри витрины. |
| `e2e/*` | **Использовать** | Переписать фикстуры под наш бэкенд, добавить сценарий полного заказа. |
| `docker/*` | **Адаптировать** | Паттерн (multi-stage, non-root, healthcheck) хороший. |
| CI `.github/workflows/ci.yml` | **Расширить** | Добавить job бэкенда с PostgreSQL. Workflows деплоя demo (k8s) — удалить из нашего форка. |

## 7. Готовность к трём клиентским каналам

- Web: готов как основа.
- Telegram Mini App: это веб-страница в WebView — **тот же `web-app` с платформенным адаптером** (детекция `Telegram.WebApp`, BackButton/MainButton, тема, viewport). Отдельное приложение не нужно.
- Mobile: Nuxt умеет SPA-сборку (`ssr: false` + `nuxt generate`) → оборачивается Capacitor. Блокер — P7 (BFF), снимается переводом сторов на прямой API-клиент. Подробно — ADR-0005.
