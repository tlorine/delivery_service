# Безопасность и соответствие требованиям

## 1. Модель угроз (MVP)
| Угроза | Мера |
|---|---|
| Доступ к данным чужого кафе | Тенант только с сервера; фильтр `tenant_id` в каждом запросе; PostgreSQL RLS; составные FK; тесты изоляции (ADR-0002) |
| Подмена цены/статуса клиентом | Входные схемы не содержат цен и статусов; расчёт только из БД; `expected_total_minor` лишь сверяется |
| Повторное оформление/двойной клик | `Idempotency-Key`, блокировка корзины, уникальные индексы |
| Подделка Telegram-пользователя | Проверка подписи `initData` токеном бота тенанта + `auth_date` (ADR-0007) |
| Подделка webhook-ов | Telegram — секрет в заголовке; платежи — проверка подписи/повторный запрос статуса у провайдера |
| Перебор токенов заказа/корзины | 256-битные случайные токены, в БД — SHA-256; ответ 404 без различия «нет/чужой» |
| Перебор паролей админки | Argon2id, rate limit на `/admin/auth/login` по IP и email, единое сообщение об ошибке |
| Спам заказами | Rate limit на `POST /v1/orders` и корзину по IP; заказ попадает в `pending`, кафе подтверждает |
| CSRF в админке | `SameSite=Lax` + обязательный `X-Requested-With` для изменяющих запросов |
| XSS | Vue-экранирование; запрет `v-html` для данных тенанта; CSP на витрине и админке |
| Утечка секретов | Секреты только в env/secret-файлах; токены ботов и ключи провайдеров в БД зашифрованы (Fernet, ключ `APP_ENCRYPTION_KEY`) |

## 2. Секреты на клиенте
| Что | Где хранится | Почему так |
|---|---|---|
| `cart_token` | cookie `SameSite=Lax`, `Secure` в production, читается JS | нужен и SSR, и браузеру; ПДн в корзине нет; утечка даёт только доступ к составу корзины |
| токен доступа к заказу | `localStorage` устройства, в URL — только id заказа | токен не попадает в историю браузера, логи прокси и `Referer` |
| контакты покупателя до оформления | `localStorage` устройства | на сервер ПДн уходят только вместе с заказом и согласием |
| сессия сотрудника | cookie `HttpOnly` (`path=/v1/admin`) или Bearer | ADR-0009 |

## 3. Авторизация
Каждый admin-эндпоинт объявляет минимальную роль; `StaffContext.require(role)` проверяет сессию, членство в тенанте из `X-Tenant-Id` и роль. Сущность загружается в контексте тенанта — id чужой сущности даёт 404 (проверено тестами для товаров, вариантов, стоп-листа, заказов).

| Роль | Может |
|---|---|
| operator | заказы (просмотр, статусы), стоп-лист, просмотр меню и филиалов |
| manager | + меню и цены, расписание, параметры филиала, зоны доставки, аналитика |
| owner | + настройки заведения, Telegram, сотрудники |

Защита от блокировки: нельзя удалить себя и последнего владельца; удаление сотрудника сразу отзывает его сессии (если других заведений у него нет). Все изменения меню, цен (со старым значением), стоп-листа, расписания, зон, настроек и состава сотрудников пишутся в `audit_log`.

## 4. Логи
Структурированный JSON. **Не логируются**: телефоны, имена, адреса, комментарии, `initData`, токены, тела запросов. Логируются id (заказа, тенанта), коды ошибок, длительности. В Telegram-уведомление кафе ПДн попадают намеренно (кафе — оператор этих данных) — фиксируется в договоре.

## 5. Транспорт и заголовки
HTTPS везде (Caddy/nginx + Let's Encrypt, в т.ч. для собственных доменов — on-demand TLS с allowlist из `tenant_domains`). HSTS. CORS для API — только домены тенантов и origin мобильного приложения (`capacitor://localhost`, `https://localhost`).

## 6. 152-ФЗ «О персональных данных» — требует проверки юристом
Технически заложено:
- Хранение в БД на серверах в РФ (требование локализации, ст. 18 ч. 5) — деплой в российском ДЦ (Selectel, Yandex Cloud, VK Cloud, Timeweb). Внешние сервисы, получающие ПДн (Telegram), — оценить как трансграничную передачу.
- Минимизация: собираем имя, телефон, адрес только для исполнения заказа.
- Согласие на обработку ПДн в checkout: чекбокс обязателен (без него API отвечает 422), время согласия — `orders.pd_consent_at`. **Не сделано:** ссылка на политику тенанта и версия текста согласия.
- Сроки хранения: ПДн в заказах обезличиваются через N месяцев (настройка, по умолчанию 3 года для бухгалтерии — уточнить), неоформленные корзины удаляются через 30 дней.
- Право субъекта на удаление: процедура обезличивания покупателя по запросу (CLI/админка — после MVP).

Организационно (не код): роли сторон (кафе — оператор, платформа — обработчик по поручению, ст. 6 ч. 3), договор-поручение, уведомление Роскомнадзора, политика обработки ПДн, модель угроз и уровень защищённости ИСПДн (ПП-1119), назначение ответственного.

## 7. 54-ФЗ «О применении ККТ» — требует проверки
- Онлайн-оплата на сайте → чек обязан сформироваться в момент расчёта. Варианты: облачная касса провайдера (ЮKassa «Чеки от ЮKassa», АТОЛ Онлайн, OrangeData) или касса кафе. Модель: `FiscalProvider` вызывается из обработчика `payment.succeeded`; в чек передаются позиции из снимка заказа (наименование, цена, количество, НДС/признак предмета и способа расчёта).
- Оплата наличными/картой курьеру или при самовывозе — чек пробивает кафе на своей ККТ; платформа не участвует. **Пилот работает в этом режиме.**
- Нужно уточнить: ставки НДС/УСН тенанта, признак агента, если деньги проходят через платформу (рекомендация — деньги идут напрямую на счёт кафе в ЮKassa, платформа не агент).

## 8. Платёжные данные
Реквизиты карт не попадают в нашу систему: оплата на стороне провайдера (redirect/виджет ЮKassa). Это выводит систему из области PCI DSS SAQ D.
