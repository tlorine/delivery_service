# ADR-0003. OpenAPI бэкенда — единственный контракт; food-schema — view-model витрины

Статус: принято · 2026-11-09

## Контекст
NextOrders описывает данные в `packages/food-schema` (Zod) и общается с бэкендом через «Gateway» — один POST с `{type, body}`. Это RPC без версионирования и без OpenAPI. Нам нужен контракт для трёх клиентов и админки, включая долгоживущие мобильные сборки.

Несоответствия food-schema нашей модели: деньги — float; нет модификаторов; многоязычные `LocaleValue[]` во всех текстах; `OrderSchema.partial()` позволяет клиенту прислать `totalPrice` и `status`.

## Решение
- Контракт — OpenAPI 3.1, генерируемый FastAPI из Pydantic-схем. Файл `backend/openapi.json` коммитится; CI проверяет, что он актуален.
- `packages/api-client`: TS-типы генерирует `openapi-typescript`, запросы — `openapi-fetch` (≈6 KB, без кодогенерации методов). Это лист графа зависимостей.
- `food-schema` **не** является контрактом API. Остаётся моделью отображения компонентов витрины, расширяется аддитивно (модификаторы, целые копейки в новых полях). Адаптер `api → view` живёт в `packages/core` — так компоненты витрины не переписываются разом.
- Gateway-протокол и BFF-роуты `packages/core/server/api/*` выводятся из эксплуатации по мере перевода сторов на `api-client`.

## Альтернативы
- Генерировать Zod из OpenAPI и заменить food-schema — переписывание всех компонентов сразу, без выигрыша для пользователя.
- Реализовать Gateway-протокол на FastAPI — сохраняет RPC без версий и проблему P4 (клиентские цены).

## Последствия
- Два набора типов на фронте с чёткой ролью: `api-client` (провод) и `food-schema` (отображение). Маппинг в одном месте и покрыт тестами.
- Изменение API → `pnpm gen:api` → TS-ошибки показывают все места, требующие правки.
