# ADR-0004. Серверная корзина и идемпотентное оформление

Статус: принято · 2026-11-09

## Решение
- Корзина хранится на сервере, принадлежит тенанту, доступна по секретному `cart_token` (32 байта, в БД — SHA-256). Клиент хранит токен (cookie на web, `CloudStorage`/localStorage в Telegram, Preferences в Capacitor) и передаёт в `X-Cart-Token`.
- В корзине нет цен. Каждый ответ корзины пересчитывается из текущего каталога; недоступные позиции помечаются, а не удаляются молча.
- Позиция = вариант + набор модификаторов (`modifier_id`, `quantity`) + количество. Одинаковые конфигурации схлопываются (`line_key`).
- `POST /v1/orders` требует `Idempotency-Key`. Внутри одной транзакции: `SELECT … FOR UPDATE` корзины → проверка инвариантов → создание заказа и снимков → корзина `checked_out`. Уникальные индексы `(tenant_id, idempotency_key)` и `orders.cart_id` — финальная защита от гонок.
- Клиент может прислать `expected_total_minor` — то, что он показал покупателю. Расхождение → `409 price_changed` с новым расчётом: покупатель не получает заказ дороже, чем видел.

## Почему не клиентская корзина
Клиентская корзина в трёх клиентах = трижды реализованная логика модификаторов и доступности. Сервер всё равно обязан всё перепроверить при оформлении. NextOrders уже использует серверный черновик — переход естественный.

## Последствия
- Каждое изменение корзины — запрос к API (как и сейчас в NextOrders). Ответ корзины содержит готовые итоги для отображения.
- Брошенные корзины удаляются задачей очистки (TTL 30 дней) — в них могут быть данные, но не ПДн: контакты передаются только при оформлении.
