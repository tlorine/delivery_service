# ADR-0006. Transactional outbox в PostgreSQL, без Redis/Celery

Статус: принято · 2026-11-09

## Контекст
Нужно надёжно уведомлять кафе о заказах (Telegram) и позже — обрабатывать события платежей. Отправка внутри HTTP-запроса теряет уведомление при сбое Telegram и замедляет оформление.

## Решение
- Таблица `outbox_events`: событие пишется **в той же транзакции**, что и изменение заказа.
- Процесс `worker` (тот же образ) выбирает события `SELECT … FOR UPDATE SKIP LOCKED`, вызывает обработчики, при ошибке — экспоненциальная задержка (`available_at`), после N попыток — `failed` (видно в логах/метриках, можно перезапустить).
- Пробуждение: `LISTEN/NOTIFY` + опрос раз в несколько секунд как страховка.
- Доставка «как минимум один раз»; обработчики идемпотентны (ключ — id события).

## Почему не Redis/Celery/RabbitMQ
Объём — единицы событий в минуту. Брокер добавляет компонент, бэкапы, мониторинг и проблему двойной записи (БД + брокер). Пересмотреть при: >~100 событий/с, нужде в планировщике сложных задач или fan-out на много потребителей.

Rate limiting в MVP — в памяти процесса API (один инстанс). При горизонтальном масштабировании — перенос на Redis или на прокси (nginx `limit_req`). Зафиксировано как техдолг.
