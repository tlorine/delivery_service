# ADR-0002. Мультитенантность: общая БД + tenant_id + RLS

Статус: принято · 2026-11-09

## Контекст
Главный критерий успеха — подключить второе кафе без копирования бэкенда. Утечка данных между заведениями (заказы, телефоны клиентов) — самый дорогой возможный дефект.

## Варианты
| Вариант | Изоляция | Стоимость эксплуатации | Миграции |
|---|---|---|---|
| БД на тенанта | максимальная | высокая (N баз, N бэкапов, пул на каждую) | N прогонов |
| Схема на тенанта | высокая | средняя; `search_path` и пулы — источник ошибок | N прогонов |
| **Общие таблицы + `tenant_id`** | логическая | минимальная | один прогон |

## Решение
Общие таблицы, у каждой тенантной таблицы колонка `tenant_id NOT NULL`. Два рубежа защиты:

1. **Приложение.** Тенант определяет только сервер (`TenantResolver`: Host → `tenant_domains`, `X-Tenant` slug для мобильного клиента, членство сотрудника для админки, бот для Telegram). Все запросы репозиториев явно фильтруют по `tenant_id` из `TenantContext`, который нельзя получить из тела запроса.
2. **PostgreSQL Row Level Security.** Приложение подключается ролью `app` без `BYPASSRLS`, не владельцем таблиц. В начале каждой транзакции выполняется `SET LOCAL app.tenant_id = '<uuid>'`. Политика `tenant_id = current_setting('app.tenant_id', true)::uuid`. Если код забыл фильтр — RLS вернёт только строки текущего тенанта; если тенант не установлен — ноль строк.

Таблицы маршрутизации (`tenants`, `tenant_domains`, `tenant_counters`, `telegram_bots`, `staff_users`, `staff_sessions`, `memberships`, `outbox_events`) не тенантные или читаются до определения тенанта (вход сотрудника, webhook бота, воркер) — без RLS, доступ только из резолвера/identity/воркера. Воркер, прочитав событие, привязывает сессию к его тенанту перед вызовом обработчиков.

Третий рубеж — составные внешние ключи `(tenant_id, x_id) → (tenant_id, id)`: даже роль-владелец не может связать строку одного тенанта со строкой другого.

Миграции выполняются ролью-владельцем (`migrator`).

## Последствия
- Тесты изоляции: два тенанта с одинаковыми slug и данными; проверка API (404 на чужие id/токены) и прямых SQL под ролью `app`.
- Кросс-тенантные операции платформы (создание тенанта, биллинг) — через CLI под ролью-владельцем, не через публичный API.
- При росте до крупных клиентов возможен вынос тенанта в отдельную БД без изменения кода (tenant_id остаётся).
