# ADR-0005. Мобильное приложение: Capacitor + SPA-сборка storefront, одно приложение платформы

Статус: принято · 2026-11-09. Модель распространения утверждена владельцем (§4): одно приложение платформы без публичного каталога

## 1. Варианты технологии
| Критерий | A. Capacitor + SPA-сборка `apps/web-app` | B. Отдельное Ionic Vue + Capacitor | C. React Native + Expo |
|---|---|---|---|
| Переиспользование кода | ~85–90%: компоненты, сторы, api-client, i18n | ~50%: сторы, api-client, i18n; UI заново на Ionic | ~15%: только OpenAPI-типы |
| UX | веб-UI, уже mobile-first; нативные жесты/переходы ограничены | нативно-подобные компоненты и навигация Ionic | нативный |
| Производительность | достаточна для каталога/корзины/формы (WKWebView/Chrome WebView) | то же | лучше на длинных списках и анимациях |
| Push | `@capacitor/push-notifications` (FCM/APNs) | то же | `expo-notifications` |
| Геолокация, нативное | плагины Capacitor | то же | модули Expo |
| Offline | кэш меню (Preferences/IndexedDB); заказ требует сети в любом варианте | то же | то же |
| Публикация/обновления | сторы; live-update веб-слоя возможен (Capgo/Appflow) в рамках правил сторов | то же | EAS Update |
| Стоимость поддержки | минимальная: одна кодовая база UI | вторая UI-кодовая база | второй стек и вторая команда |

## 2. Решение по технологии
**Вариант A.** `apps/mobile` — Capacitor-оболочка; веб-слой — `nuxt generate` из `apps/web-app` с `ssr: false` и `NUXT_PUBLIC_PLATFORM=capacitor`. Платформенная специфика — `packages/core/app/platform/capacitor` (push, deep links, status bar, back-кнопка Android, хранение токенов).

Условия, при которых переходим к B: UX-тест на реальных устройствах показывает, что веб-навигация воспринимается «как сайт» и это влияет на конверсию. Переход к B дешёвый — сторы и api-client уже общие. React Native — только при требованиях, недостижимых в WebView (не выявлены).

Предпосылка: перевод сторов с BFF (`/api/*` в Nuxt server) на прямой `api-client` — без этого SPA-сборка не работает. Это и так нужно для Telegram.

## 3. Как мобильный клиент определяет заведение
Нет Host → заголовок `X-Tenant: <slug>`. Slug — публичный идентификатор витрины, не даёт прав. Источник slug: deep link / QR (`https://app.<platform>/t/<slug>`), сохранённый выбор, или константа white-label сборки.

## 4. Модель распространения — решение владельца продукта
| | Одно приложение платформы | White-label на кафе |
|---|---|---|
| Публикация | один аккаунт разработчика, одно ревью | аккаунт/листинг на каждое кафе; Apple требует, чтобы приложения-«шаблоны» публиковались от имени клиента (Guideline 4.2.6) |
| Бренд кафе в сторе | нет (бренд внутри после открытия) | да |
| Риск «маркетплейса» | есть, если показывать список заведений | нет |
| Стоимость | низкая | линейно растёт с числом кафе |

**Рекомендация:** одно приложение платформы **без каталога заведений**: заведение открывается по ссылке/QR из витрины или Telegram-бота кафе; в приложении — только «мои заведения». White-label — платная опция из того же кода (конфиг сборки: slug, иконка, цвета), не отдельная ветка. Решение зафиксировать с владельцем до публикации в сторы.

## 5. Реализация (2026-11-09)
Выполнено по варианту A: `apps/mobile` (Capacitor 8.5.3, Android + iOS), SPA-сборка `apps/web-app` (`generate:mobile`), «Мои заведения», deep links, раздельные корзины, надёжное хранилище. Подробно — [mobile.md](../mobile.md).

## 6. Ограничение готовности
Мобильное приложение не объявляется готовым без проверки на реальных Android и iOS устройствах (сборка iOS требует macOS + Xcode и аккаунт Apple Developer).
